## Assumptions (smallest reversible)

- A1: extensibility = `Entity.kind`/`Relationship.kind` stay validated strings; enums list known kinds. Graphs with future kinds decode unchanged.
- A2: canonical = exact bytes. Kind lowercase snake_case, domain lowercase no whitespace, identifier printable + trimmed (case preserved: `getPayment`, `GET:/…`). `service:python:Payments` ≠ `service:python:payments` → two nodes.
- A3: same id + different content → `GraphError` (no merge, no last-write-wins). Same for edges with same `(source, kind, target)` but different confidence/evidence. Analyzers must agree or use distinct ids.
- A4: edges must reference existing entities (no dangling / auto-created nodes).
- A5: uncertainty on edges = `Relationship.confidence` (required, no default) + `unknowns` (required at UNKNOWN), mirroring `Finding`.
- A6: topology nodes = kinds `service`, `client`, `gateway`, `external_api` (§58 example has client + gateway boxes); edges = explicit `CALLS`/`DEPENDS_ON` between those. No roll-up from endpoint-level calls (would be inference). `ROUTES_TO` excluded per spec wording.
- A7: `reachable()` excludes the start node unless a cycle returns to it.
- A8: `ServiceGraph.from_dict` accepts any `1.x` schema_version, rejects other majors.

## Open risks

- R1: strict conflict rejection (A3) may be too rigid once multiple analyzers describe one service (e.g. differing attributes); likely next step is evidence-union for edges + explicit attribute-merge policy — needs product decision.
- R2: topology kind set (A6) is a guess; `load_balancer`, `async_channel` may belong later.
- R3: `Relationship.confidence` now required — breaking for any external producer of serialized relationships (none exist yet).
- R4: `ServiceTopology` drops per-edge confidence; an UNKNOWN `CALLS` edge appears as a plain dependency. Consumers needing certainty must query the graph.
- R5: `README.md` has an uncommitted logo change not made by this run — left untouched.
